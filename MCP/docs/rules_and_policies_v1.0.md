# MCP - 핵심 규칙 및 정책 정의서 v1.0

## 1. 개요 (Overview)

본 문서는 MCP(Model-Callable Procedure) TRPG 시스템의 구체적인 작동 방식을 정의합니다. 이 문서는 시스템의 '물리 법칙'에 해당하는 **핵심 월드 규칙**과, 각 AI 마스터가 따라야 할 '윤리 강령'이자 '행동 지침'인 **AI 마스터 정책**으로 구성됩니다. 모든 컴포넌트는 본 문서에 정의된 규칙과 정책을 준수하여야 합니다.

## 2. 핵심 월드 규칙 (Core World Rules)

### 2.1. 시간 규칙 (Time Rules)

*   **월드 클럭 (World Clock):**
    *   시스템은 `월드 클럭`을 통해 게임 세계의 시간을 지속적으로 추적합니다.
    *   **기본 틱 (Default Tick):** 플레이어가 활발히 행동하는 동안, `월드 클럭`은 **10분**을 1 '틱(Tick)'으로 하여 자동으로 시간이 흐릅니다. `서사 엔진`은 이 틱을 기준으로 일부 배경 이벤트(예: 역병 확산)를 처리할 수 있습니다.
*   **시간 소모 행동 (Downtime Actions):**
    *   플레이어가 명시적으로 시간을 보내는 행동을 할 경우, 해당 시간만큼 `월드 클럭`이 진행되고, `서사 엔진`의 `simulate_downtime` MCP가 호출됩니다.
    *   **휴식 (Rest):** '짧은 휴식'은 1시간, '긴 휴식'은 8시간을 진행시킵니다.
    *   **여행 (Travel):** 이동 거리에 따라 결정된 시간이 진행됩니다. (예: 이웃 마을까지 '반나절', 다른 지역까지 '3일')

### 2.2. 판정 규칙 (Skill Check Rules)

*   **기본 공식:** 모든 스킬 판정은 다음의 공식을 따릅니다.
    > **1d20 (20면체 주사위 1개) + 관련 능력치 보정치 + 기타 보너스**
*   **성공/실패:** 판정 결과값이 목표 난이도(DC, Difficulty Class)와 같거나 높으면 성공, 낮으면 실패입니다.
*   **난이도 (DC) 설정 가이드라인:**
    *   **매우 쉬움 (DC 5):** 거의 실패하지 않음.
    *   **쉬움 (DC 10):** 일반적인 전문가라면 성공할 수 있음.
    *   **보통 (DC 15):** 해당 분야에 재능이 있거나, 상황이 유리해야 성공할 수 있음.
    *   **어려움 (DC 20):** 진정한 전문가만이 성공할 수 있음.
    *   **매우 어려움 (DC 25):** 해당 분야의 대가조차 성공을 장담하기 어려움.
    *   **거의 불가능 (DC 30):** 초인적인 능력이 필요한 수준.

### 2.3. 경제 규칙 (Economy Rules)

*   **자원 가용성 (Resource Availability):**
    *   `WorldState`의 `regional_market` 데이터는 각 지역의 자원 가용성을 `[high, medium, low, depleted]` 4단계로 추적합니다.
    *   **가용성 변동 규칙:** 특정 `Project`나 플레이어의 대량 구매로 인해 한 지역의 자원이 단기간에 소모될 경우, `서사 엔진`은 해당 자원의 `availability`를 한 단계 낮출 수 있습니다. (예: `high` → `medium`).
    *   자연 회복: 시간이 지남에 따라 `availability`는 서서히 다시 회복될 수 있습니다.

## 3. AI 마스터 정책 (AI Master Policies)

### 3.1. 오케스트레이터 정책 (Orchestrator Policy)

*   **핸드오프 규칙 (Handoff Rules):** `오케스트레이터`는 플레이어의 의도를 분석하여, 다음 표에 따라 책임 마스터에게 제어권을 이양해야 합니다.

| 플레이어 의도 (Intent) | 담당 마스터 | 예시 |
| :--- | :--- | :--- |
| `explore_area`, `hear_rumors` | 🏡 거점 마스터 | "마을을 둘러보고 싶어", "뭐 재밌는 소문 없어?" |
| `enter_dungeon`, `fight_monster` | ⚔️ 던전 마스터 | "저 동굴에 들어가 보자", "오크를 공격한다" |
| `develop_relationship` | 🤝 관계 마스터 | "홀리의 슬픈 표정에 대해 더 알아보고 싶다" |
| `invest_in_domain` | 🏛️ 영지/세력 마스터 | "망루를 재건하는 데 투자하고 싶습니다" |

### 3.2. 서사 엔진 정책 (Narrative Engine Policy)

*   **이벤트 큐 관리 정책:**
    *   `timed_event_queue`의 이벤트 충돌 시, 다음 규칙에 따라 처리합니다.
        1.  **우선순위(Priority) 규칙:** `priority` 값이 더 높은 이벤트가 항상 먼저 처리됩니다. (9가 1보다 높음)
        2.  **상태 변경 규칙:** 우선순위가 높은 이벤트의 결과로 인해, 우선순위가 낮은 이벤트의 실행 조건이 깨지면, 해당 이벤트는 자동으로 큐에서 제거됩니다.
*   **위험 요소(Risk Factor) 관리 정책:**
    *   `Project`의 `risk_factors` 판정은 `simulate_downtime`이 호출될 때마다, 경과된 시간을 기준으로 판정 횟수를 결정하여 실행합니다. (예: 30일 경과 시, 10일마다 판정하는 위험이라면 3회 판정)
    *   `서사 엔진`은 위험 판정의 결과가 '촉발'일 경우, **절대 직접 결과를 적용하지 않습니다.** 반드시 담당 마스터(주로 `영지/세력 마스터`)에게 `risk_triggered` 이벤트를 보내, 플레이어에게 선택지를 제시할 기회를 주어야 합니다.

### 3.3. 실행 마스터 공통 정책 (Common Execution Master Policies)

*   **최우선 정책: 플레이어 주도 서사 (Player Agency First)**
    *   **원칙 1: 결과를 통보하지 말고, 사건을 제시하라.** 시스템은 플레이어의 개입 없이 발생한 사건의 결과를 일방적으로 통보해서는 안 됩니다. 대신, 사건이 발생할 '위험'을 제시하고, 플레이어가 어떻게 대응할지 '선택'하게 만들어야 합니다.
    *   **원칙 2: 실패는 끝이 아니라, 새로운 분기점이다.** 플레이어의 판정 실패는 이야기의 끝이 아니라, 새로운 상황(예: NPC의 불신, 다른 해결 경로 모색)을 만들어내는 또 다른 서사적 분기점이어야 합니다.
*   **데이터 해석 정책:**
    *   **추상적 데이터를 구체적 서사로:** `condition_tags: ["damaged_wall"]` 와 같은 구체적인 상태 태그를 우선적으로 사용하여 묘사해야 합니다. LLM 마스터는 이 태그를 바탕으로 "망루의 벽 일부가 파손되어 있습니다" 와 같이 명확하고 일관된 묘사를 생성해야 합니다.
    *   **다차원적 데이터 활용:** `RelationshipState`의 `trust`, `empathy` 같은 여러 벡터 값을 종합적으로 고려하여, NPC의 반응을 단편적이지 않고 입체적으로 생성해야 합니다.
